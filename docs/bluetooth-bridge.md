# 蓝牙连接（0.15.0）

Windows 与 macOS 均已实现等待端和主动端，连接角色不决定谁控制谁。同系统与跨系统共用桥接协议，建立后均可双向控制、传文件、共享剪贴板，沿用接收方弹窗授权。

| 组合 | 等待端 | 主动端 |
| --- | --- | --- |
| Windows ↔ Windows | 任一端 | 另一端 |
| macOS ↔ macOS | 任一端 | 另一端 |
| Windows ↔ macOS | 任一端 | 另一端 |

**验证边界：新增角色和组合已经实现，但本机只有 Windows 构建环境。自动化模拟不能替代射频连接验证；macOS 原生辅助程序编译、两台 Windows、两台 Mac，以及 Windows 主动连接 Mac 均需实机验收。**

## 桌面操作

1. 两台设备更新到 0.15.0，完整保留蓝牙组件。在系统设置中开启蓝牙并完成首次配对。
2. 一端进入“设备连接 → 蓝牙直连”，选择“等待对方连接”，点击“等待蓝牙连接”。界面显示本机蓝牙地址和当前频道。
3. 另一端选择“主动连接对方”，输入等待端显示的地址、频道，点击“建立蓝牙连接”。每次重新等待的频道可能变化，使用当次显示的值。
4. 双方显示“蓝牙已连接”后，任一端点击“连接蓝牙设备”，再按需请求控制、共享剪贴板或发送文件。连接本身不授予这些权限。
5. 更换连接角色前先点击“停止蓝牙”；停止或退出会释放链路并中断其上的传输。两端不要同时等待或同时主动连接。

等待对方加入可以一直保持。启动或连接握手超过约 30 秒会失败并释放桥接进程，可修改参数后重试。发起端地址错误、频道变化、未配对或蓝牙权限未授予时，请按具体错误检查，不要去创建 Wi-Fi 网络。

## 实现

- Windows：经典蓝牙 Winsock RFCOMM 同时支持监听与主动连接，沿用认证与链路加密选项。
- macOS：IOBluetooth 发布临时 SDP 服务并接收传入 RFCOMM，或主动打开对方频道；仅接收已配对设备，建立时请求认证。停止进程后临时服务由系统回收，不创建持久系统服务。
- 多路复用流编号按等待/主动角色分配奇偶数，与操作系统无关；同一链路允许两端同时发起应用连接。
- Mac 辅助进程先发送有限长状态行，再传二进制数据；Rust 保留读取缓冲区中的握手数据，防止状态与数据紧邻时丢帧。
- 应用协议仍为 7，蓝牙桥接握手仍为 PDLBT001。旧版只具备原来的角色组合，建议两端一起更新。旧 `--mac` 参数保留为 `--connect` 的兼容别名。

CLI（仅排错时使用，勿与桌面的桥接进程同时启动）：

```text
bluetooth_bridge --listen
bluetooth_bridge --connect AABBCCDDEEFF 7
```

Mac 原生构建及安装见 [Mac 说明](macos-quickstart.md)，GitHub 自动生成应用包见 [发布指南](releasing.md)。本应用不自动完成系统配对，也不修改防火墙、系统热点或蓝牙开关。应用层尚未加密，只连接可信设备。

接口依据：[Microsoft Bluetooth connect](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-connect)、[Apple 蓝牙服务发布](https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/Bluetooth/BT_Develop_BT_Apps/BT_Develop_BT_Apps.html)。

## 实机验收

每种组合均测试一端等待、另一端主动，之后互换角色重试。临时断开两端 Wi-Fi/有线连接可排除误走局域网。链路就绪后，分别从两端发起控制、发送文件、请求剪贴板共享，核对弹窗和拒绝行为；停止蓝牙应停止相关通信并恢复本地输入。还应覆盖错误频道超时、等待中停止、再次开启时频道刷新，以及已有会话不被第二台设备抢占。
